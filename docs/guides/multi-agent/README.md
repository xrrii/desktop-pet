# PetDock 多代理角色手册

状态：Active。定义日期：2026-09-11。适用于 `desktop-pet`、`petdock-cloud` 和 `petdock-web` 的开发协作。

角色按任务目标、读写边界、输入、执行步骤和交付证据定义。每个角色都使用 [共同约定](common.md)，每次分派都附上 [任务单](task-template.md)。角色名称是项目协作用语，不是应用 API 中的代理类型。

## 角色与启用时机

| 标识 | 定义 | 启用条件 |
| --- | --- | --- |
| coordinator | [主代理／技术负责人](coordinator.md) | 当前对话的主代理承担，负责需求到交付的完整闭环 |
| cloud | [Cloud 后端开发](cloud.md) | 涉及云端接口、授权、额度、AI 数据面或契约 |
| web | [Web 前端开发](web.md) | 涉及官网、管理后台、浏览器交互或 Web API 接入 |
| desktop | [Desktop 客户端开发](desktop.md) | 涉及 Electron、Python Runtime、本地能力或契约消费 |
| qa | [测试验收](qa.md) | 需要独立验证用户流程、权限或跨项目回归 |
| reviewer | [代码审查](reviewer.md) | 需要独立审查业务正确性、安全、兼容性或迁移 |
| release | [发布运维](release.md) | 涉及打包、部署配置、迁移上线或回退方案，按需启用 |

## 如何使用

在任务开始时可这样要求主代理：

> 按 PetDock 多代理角色手册处理本需求。先明确验收标准和文件归属，再按依赖分派；本次需要独立测试和代码审查。由主代理整合最终结果。

主代理向子代理提供已确认的仓库绝对路径，并要求依次读取共同约定、对应角色文件和任务单。新检出或 worktree 中必须重新确认路径；本手册不固定本机目录、模型或生产配置，代理并发执行下述硬性上限。

这些 Markdown 文件可在分派时直接使用；本次仅定义角色与协作流程，未创建自定义代理的应用配置，也未启动开发子代理。角色名称和只读要求属于任务约束；实际工具权限由运行环境决定。

## 并发硬性上限

同一任务及其所有跨仓子任务合计最多两个代理，包含主代理：主代理始终占用一个名额，同时最多一个未结束的子代理。主代理等待结果时仍占名额；子代理等待依赖、输入或工具执行时也占名额。

创建、恢复或向已有子代理续派任务前，主代理必须核对状态。当前子代理完成，或停止已确认且其在途工具操作已结束后，才能释放名额并调度下一个角色。已完成且未续派任务的空闲代理不占执行名额。

超出上限的任务排队；跨仓库、worktree、切换角色或另开执行线程均不能绕过上限。子代理禁止再派生子代理。运行环境允许更高并发时仍以两个为上限，环境上限更低时服从更低上限。

## 分派与依赖

- 当前主代理承担 coordinator，避免为协调本身额外启动代理。
- 只把有明确交付、能够独立推进的工作分出去。七个角色按需轮换，任一时刻最多主代理与一个子代理共同推进。
- 跨端变更先由 Cloud 完成权威契约及规定验证，再允许 Web 生成类型、Desktop 同步快照和适配。契约未定时，各端可处理不依赖接口的布局或本地准备。
- 同一文件只有一名写入负责人。特别指定契约、生成文件、锁文件、共享配置、迁移编号和部署文件的负责人。
- 实现稳定后，测试与审查子代理依次执行；主代理可同时处理不影响被测快照的整合工作。涉及同一数据库、端口、构建输出或测试文件的操作需要串行或隔离。
- 主代理记录被验证的提交或工作区快照。修复后复验受影响的检查；旧快照的通过结果不能代表新修改已通过。

## 典型组合

下表列出参与角色和交接顺序，各子代理依次执行；主代理可同时承担一个明确归属自己的工作项。

| 任务 | 分工 |
| --- | --- |
| 文案、样式等小改动 | 主代理或对应开发角色完成，按影响选择已有检查 |
| 管理授权与访问统计 | Cloud + Web；Desktop 按需同步契约；QA 和 Reviewer 验收；Release 准备增量部署 |
| 本地知识库优化 | Desktop；QA 检查检索质量和兼容性；Reviewer 检查数据与进程边界 |
| 跨端官方能力 | Cloud 先定契约，各端分工适配，QA 集成验收，Reviewer 独立审查 |

## 定义质量的判断标准

好的任务单应让代理能回答：要改变什么用户行为、哪些文件由我修改、依赖何时就绪、如何证明完成、问题交给谁。结束时应能从证据识别实现结果、验证结果和未完成项。

角色定义的权威源只维护在本目录；另外两个仓库通过各自 `AGENTS.md` 定位本手册，避免维护三份不同的角色提示词。独立检出时由主代理提供手册的实际位置；缺失手册不阻断与其无关的常规开发。
