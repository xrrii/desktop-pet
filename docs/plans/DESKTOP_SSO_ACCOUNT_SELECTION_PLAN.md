# Desktop SSO 与账号选择方案

状态：Draft，仅完成方案，尚未实现。日期：2026-09-11。

## 1. 目标与已确认决定

用户在系统浏览器已经登录 `petdock.site` 时，主动点击桌面登录，应能确认复用官网账号，也能选择其他账号。每次主动登录都展示账号选择，不静默替用户登录。

- 官网为账号 A、桌面选择账号 B 时，官网继续保持 A，仅桌面登录 B。
- 同一账号已经授权过 Desktop，且权限未变化时，选择账号后跳过重复权限页；首次授权或权限扩大继续使用现有 Consent。
- 桌面重启自动恢复登录已经正常，本需求针对主动点击登录的浏览器交互。

复用前提是桌面打开的系统浏览器及其用户配置中存在有效官网会话。其他浏览器、隐私窗口或不同浏览器配置应提供正常登录入口。

## 2. 当前实现

- Desktop 的 `src/main/managed/managedOAuthClient.ts` 每次发起授权都携带 `prompt=login`。
- Cloud 的 `OAuthAccountReauthenticationFilter` 清除账号主机当前 Session；登录成功后 `OAuthBrowserController` 消费该提示并恢复授权请求。
- Web 普通账号 API 指向 `api.petdock.site`，OAuth 页面使用 `account.petdock.site`；两者使用独立的 Host-only `__Host-petdock_web_session`。
- 已有 Spring Session／Redis、Session ID 与 CSRF 轮换、Authorization Code + PKCE，以及按用户、Client、权限记录的 Consent。

本需求同时涉及 Desktop 登录策略、Cloud 登录态衔接和 Web 账号选择。仅移除 `prompt=login` 无法复用 API 主机的官网会话。

## 3. 页面与用户流程

### 官网已登录

桌面点击登录后，系统浏览器进入受控授权流程，跳转到官网中的专用账号选择页面。页面使用现有官网 Session API 获取当前账号，不读取 Cookie 内容。

建议页面文案：

```text
登录 PetDock Desktop

当前官网登录账号
显示名称（@用户名）

[使用此账号继续]
[使用其他账号]
[取消]

为桌面选择其他账号不会切换当前官网登录账号。
```

用户点击“使用此账号继续”后才允许建立本次账号中心认证。首次授权或权限扩大时进入现有权限确认页；已有相同权限 Consent 时直接完成授权并返回桌面。

账号选择和权限确认是独立行为：已有 Consent 也不能跳过本次账号选择。按钮使用“继续”，不在首次授权时提前宣称授权完成。

### 使用其他账号

进入账号主机的本次授权登录页面，输入账号 B 的用户名和密码。此分支必须重新认证，不能被账号主机残留 Session 自动跳过。认证成功后按 B 自己的 Consent 判断是否显示权限页。

账号 A 的 API 主机会话保持有效，账号主机允许建立 B 的会话。下次桌面主动登录时，若官网仍登录 A，仍优先展示 A，不自动沿用账号主机的 B。

### 未登录与异常状态

- 官网无有效会话：明确提示当前浏览器未登录官网，提供账号登录入口。
- 账号主机另有有效会话时，可在账号主机显示该账号供用户确认，并标明“账号中心当前账号”；提供其他账号入口，不冒充为官网当前账号，也不自动登录。
- 官网会话读取失败：显示重试和正常登录入口，不把网络故障标记成退出。
- 页面展示 A 后，官网在另一标签页换号、退出或改密：继续时重新校验，失配则刷新选择，不能静默改用新账号授权。
- 取消：终止本次事务，通过原已校验的 OAuth 请求返回标准取消结果；不新增桌面 Token 或设备，不退出官网。
- 关闭页面不能保证即时通知桌面，保留桌面取消按钮和现有 5 分钟等待超时；超时后重新发起。

## 4. 推荐技术路线

保留两个主机各自的安全 Cookie，在现有控制面内增加受控的一次性登录态衔接。这样可以直接消费上线前已有的有效官网 Session，支持本次“官网账号供桌面选择、两边可使用不同账号”的范围。

这是新增的认证安全边界，需要明确事务绑定、一次性消费和独立审查。最终桌面授权仍使用标准 OAuth、Consent、PKCE、Token 交换和设备注册。

### 授权事务与账号选择

1. 新 Desktop 主动登录拟采用标准 `prompt=select_account` 表达账号选择意图。Cloud 必须显式实现该语义并验证框架行为，不能假定现有 Spring 配置已自动支持。
2. Cloud 在进入选择流程前校验 Client、scope、redirect URI、PKCE 及其他必要参数，创建短期事务，绑定发起浏览器的账号主机会话。
3. 原始授权上下文保存在服务端；官网页面只接收高熵事务标识，不接收完整 OAuth 参数供其重新拼接。
4. 账号选择门禁位于可能复用已有账号会话、Consent 并签发授权码之前。服务端确认选择完成后，一次性消费选择提示，再恢复原始标准授权，避免循环跳转。
5. 每次尝试使用独立事务标识，不能只靠现有单槽位 SavedRequest 管理所有标签页。会话轮换导致旧尝试无法继续时，明确终止旧尝试，不覆盖其他请求或串用账号。

### 复用官网账号的衔接

1. 官网选择页通过 `api.petdock.site` 获取当前浏览器的 Web Session。
2. 用户明确确认后，使用来源 Session 和现有 CSRF 机制提交衔接请求；服务端再次核对当前用户、页面确认的身份、账号有效性和事务状态。
3. 生成仅限本次事务的一次性凭证，绑定源 Session、用户、目标账号主机会话、Client 和原始授权上下文。建议凭证有效期 60 秒，整体事务不超过现有 5 分钟授权窗口；参数在契约阶段登记。
4. 凭证仅通过当前浏览器的受控响应和表单 POST 交给固定账号主机接收端点，不放入 URL、Storage、分析事件或日志。仅知道事务标识不能查询、换取凭证或轮询取得登录结果。
5. 账号主机验证真实目标会话 Cookie、来源、完整绑定、源 Session 仍有效、账号状态及期限，再原子消费凭证。复制事务链接或凭证到另一浏览器不能完成交接。
6. 验证通过后用框架机制建立账号中心认证，轮换 Session ID 和 CSRF，并安全迁移本次事务上下文，再继续原始 OAuth 请求；这一步本身不签发桌面 Token。

### 其他账号与身份一致性

- 其他账号分支只影响账号主机认证，不向官网 API 发起退出或换号。
- 新流程显式保留、迁移和核对授权事务，不能直接清空 Session 而丢失原始请求或绑定。
- 用户选择的账号固定于本次事务；进入 Consent 和签发授权码前核对当前认证仍属于该账号，不一致则重新选择或终止。
- 旧 Desktop 的 `prompt=login` 行为继续兼容。新流程与旧流程分别验证，正常会话恢复继续走现有 Refresh Token 路径。

## 5. 数据、安全与失败处理

- 原始 Cookie 保持 Host-only、Secure、HttpOnly、SameSite=Lax；Web 和 Desktop 均不读取其内容，官网不接触桌面 Access／Refresh Token。
- 使用现有 Redis 保存短期事务、凭证摘要与消费状态，过期清理；预计无需新增长期业务表，具体持久化需求在实现阶段复核。
- 凭证原子消费；错误浏览器的尝试不能消耗正确浏览器的有效凭证。过期、重放、状态失配返回明确错误。
- 新增 JSON 写接口沿用 Session／CSRF。账号主机表单接收端点以严格 Origin、目标会话绑定和一次性凭证保护，仅精确配置该端点，不关闭全局 CSRF。
- 恢复和返回地址固定且经服务端校验。取消只回原始已验证 loopback；畸形授权请求停留在安全错误页。
- 专用页面和衔接响应使用 no-store、no-referrer 和必要 CSP；不接入访问统计，不在浏览器历史、错误页和日志中暴露凭证。
- 日志只记录阶段、稳定原因码、耗时及独立的非敏感请求关联标识，不记录用户凭据、Cookie、OAuth state、完整回调 URL 或衔接凭证。
- Redis／Session／衔接服务失败时提示重试或使用正常登录，不能把失败当作用户已确认并继续授权。
- 多标签页、双击、过期和账号撤销以服务端事实为准，均纳入验证。

## 6. 三仓改动与角色安排

| 角色 | 计划工作 |
| --- | --- |
| Cloud | 先更新权威契约、决定登记、样例和错误行为，再实现选择调度、短期事务、登录态衔接和旧客户端兼容 |
| Web | 官网账号选择页、其他账号分支、取消和异常状态；Consent 显示当前账号；更新生成类型与精确 Nginx 路由 |
| Desktop | 主动登录的交互意图与测试、契约快照同步、系统浏览器与打包态授权验证 |
| QA | 三主机真实 HTTPS、两种账号分支、首次／重复授权、异常及旧版回归 |
| Reviewer | 独立审查登录 CSRF、跨浏览器重放、事务绑定、身份混淆、开放重定向与会话轮换 |
| Release | Cloud／Web 增量部署、兼容验证、新版 Desktop 发布及回退说明 |

主代理负责整合；包含主代理最多两个代理并行，各子代理按依赖依次执行，任务单指定共享文件负责人。

现有接口不具备上述衔接能力，需要新增接口；路径、字段和错误码在 Cloud 契约阶段定义，本方案不将拟新增接口当成已存在的接口。

Cloud 权威 `DESKTOP_OAUTH.md`、`WEB_IDENTITY_AND_SESSION.md`、安全边界及决定登记中的相关条款需要协调更新，再整体同步 Desktop 快照。历史文档中强制登录、跨主机会话及交互页面的旧规则应明确标注被替代。

## 7. 验收标准

| 场景 | 必须达到的结果 |
| --- | --- |
| 官网 A；首次授权 | 显示 A，选择后无需密码，确认权限后桌面登录 A |
| 官网 A；已有相同权限授权 | 仍显示选择，确认后跳过重复权限页 |
| 官网 A；选择 B | 输入 B 凭据并按 B 的权限授权，官网继续保持 A |
| 官网 A；账号中心残留 B | 优先提供 A，不能自动登录成 B |
| 官网未登录 | 正常登录或明确确认账号中心有效会话；仍可选择其他账号 |
| 权限扩大 | 进入新的 Consent 确认 |
| 展示后换号、退出、改密或账号删除 | 重新选择或终止，不能沿用失效身份 |
| 双击、多标签、返回与刷新 | 不重复消费、不串号、不产生未经确认的授权 |
| 跨浏览器复制、过期或重放 | 拒绝交接，不生成错误会话、Token 或设备 |
| 取消、拒绝、关闭页或超时 | 明确结束或等待原超时，不退出官网，不新增桌面登录 |
| Cloud／Redis 不可用 | 明确错误及恢复路径，不假成功 |
| 旧 Desktop、重启与正常续期 | 旧登录仍可用，已有会话正常恢复 |

自动验证包含 Cloud 契约、单元和 Redis 集成测试，Web 状态与 E2E，以及 Desktop 的请求参数、PKCE、回调和恢复回归。跨域验收使用 `site`、`api`、`account` 三个不同主机的受信 HTTPS 与真实系统浏览器；同一 localhost 的不同端口或 Mock 不能证明 Cookie 隔离和 SSO 正确。

## 8. 发布与完成判定

先发布兼容旧 Desktop 的 Cloud 和 Web，再发布新版 Desktop。建议为新流程增加独立开关，关闭时新版请求回退到正常账号密码登录，不影响已存在的桌面会话。

增量部署以最终提交和配置为准。实现完成、自动测试通过、真实 HTTPS 联调通过与生产部署完成分别记录。

两项用户体验决定已确认。本文件仅为方案，不表示接口已实现、测试已执行或生产已部署。
